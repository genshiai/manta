# なぜ Manta を、医師がゼロから作るのか

— 設計思想と、技術選定の記録 —

> README は「何を・どう作るか」。この文書は **「なぜ作るか」「なぜこの作り方を選んだか」**、つまり作者の意図と設計判断の記録です。
> Manta はプロセスエコノミー（[ADR 0005](decisions/0005-oss-process-economy-and-license.md)）として、この「なぜ」も含めて公開します。

---

## I. なぜ、いま、これを作るのか

<!-- ▼ たたき台: 長島さんの声で自由に上書きしてください -->

### AI エージェントが動くカルテを

私が作りたいのは、**AI エージェントが当たり前に動く、次世代の電子カルテ** です。

カルテに記録する。オーダを出す。病名を整理する。算定の不備に気づく。レセプトを点検する。退院サマリを下書きする——こうした仕事の多くを、AI エージェントが医師や医療事務の隣で動いてこなす。人間は、判断と確認という、人間にしかできないことに集中する。そういう働き方を、ソフトウェアの側から実現したいのです。

ただし、エージェントが力を発揮するには前提があります。**データが、標準規格で開かれていること。** 閉じた独自形式の中では、AI も外部サービスも自由には動けません。だから Manta は **FHIR** を土台に据え、できるだけ広く外部システムとつながれる、理想的なデータ連携の形を目指します。そして、日本の医療を実際に回すのに欠かせない **レセコン（医事会計・レセプト）** も、その上に内包します。**カルテが主役、FHIR が土台、レセコンは必要だから載せる**——この順番を、Manta は崩しません。

### これは、実験でもある

正直に打ち明けると、Manta はプロダクトであると同時に、ひとつの **実験** です。

AI コーディングが急速に一般化し、**ごく少数の人間が、AI の力を借りて、相当の分量と品質のソフトウェアを現実に作れる**——その可能性が、いまはっきり見えてきました。電子カルテのように大きく複雑なシステムを、巨大なチームではなく、小さな人数 + AI でどこまで作れるのか。Manta は、それを本気で確かめにいくプロジェクトでもあります。

### 巨人の肩の上で —— オープンソースという考え方

そして、この挑戦は裸一貫ではありません。私たちは **オープンソースの長い系譜** の上に立っています。

最も成功したオープンソースは、おそらく Linux です。いま世界中のサーバーが、そしてほぼすべての Web サービスが、Linux の上で動いています。このコードを記録している Git でさえ、そうしたオープンソースの文化の中から生まれました。誰かが無償で積み上げてくれた土台の上で、私たちは今日もコードを書いている。

その **OSS の力** と、**AI によるエンパワーメント**。この二つを受け取って、新しいカルテを作る。だから Manta も、当然オープンソースにします。受け取った恩を、次へ渡すために。

### 正直に言うと

これで既存ベンダーをすぐ置き換える、市場を奪う——そんなことは、正直、夢物語でしょう。電子カルテの導入は重く、現場の信頼は一朝一夕には築けません。それは分かっています。

それでも、問いたいのです。**AI エージェントが自由に動く時代に、FHIR にもモダンウェブにも対応していないレガシーなシステムを、私たちはいつまで使い続けるのか。** その呪縛から、そろそろ離れていいはずだ。

Manta は、勝つための製品というより、**「カルテはこうあるべきだ」という理想を、動くコードで示す試み** です。理想が一つでも形になれば、業界全体の景色は少し変わる。私はそう信じています。

## II. 設計の根っこにある 3 つの確信

技術選定の前に、Manta が「何を曲げないか」を 3 つに言語化しています。すべての実装判断は、この 3 つに従属します。

### 1. 正本はカルテである

Manta はカルテとレセコンを同じプラットフォームに持ちますが、**真実の源（source of truth）はあくまでカルテ・オーダ・病名** です。会計やレセプト（`ClaimDraft`）は、そこから導かれる **派生データ** にすぎません。

なぜこだわるのか。カルテ UI を「レセコンの入力画面」に寄せると、医師の自然な臨床ワークフローが、請求の都合（算定粒度・コード体系）に侵食されるからです。実際、既存の多くの製品がこれで使いにくくなっています。Manta は逆向きに設計します。**臨床が先、請求は後** （[ADR 0004](decisions/0004-receipt-gateway-and-ai-claims-assist.md)）。

### 2. AI は確定しない。人間が確定する

Manta は AI ファーストですが、**AI に最終決定をさせません**。AI の役割は「算定漏れ・病名不足・コメント不足・重複・病名とオーダの不整合」などを **説明付きで提示する候補生成とレビュー補助** に限定します。会計送信・レセプト請求の確定前には、必ず人間の確認を挟みます（[ADR 0004](decisions/0004-receipt-gateway-and-ai-claims-assist.md)）。

医療と請求は、間違いが患者と医療機関に直接跳ね返る高リスク領域です。「AI が全部やってくれる」は、この領域では無責任になりうる。**AI は最強の副操縦士であって、操縦桿は人間が握る** ——これは譲りません。

### 3. 「なぜそう決めたか」を残す

Manta の意思決定は [ADR（Architecture Decision Records）](decisions/) に、1 ファイル 1 決定で時系列に積み上げます。後から `Superseded by NNNN` で相互リンクできるので、**方針転換（紆余曲折）ごと自然に記録** できます。

これは単なる開発作法ではありません。プロセスエコノミーの中核です。外部のコントリビューターも ADR の PR で意思決定に参加できる——「決定の透明性」こそが、医療機関とコミュニティの信頼を生むと考えています。

## III. なぜ、この技術スタックなのか

### バックエンド：FastAPI + SQLAlchemy 2 + PostgreSQL + Alembic

地味でも、**枯れていて速く、型と非同期に強い** 構成を選びました。FastAPI は OpenAPI を自動生成し（`/docs`）、Pydantic で入出力を型で守れます。SQLAlchemy 2 + Alembic で、スキーマの変更履歴を版管理します。派手さより、医療データを扱う土台としての堅牢さを優先しています。

#### なぜ「モジュラーモノリス」なのか（最初から分割しない）

マイクロサービスにはしません。`karte` / `rececon` / `gateway` などの **境界はコード上で明確に引く** が、デプロイは単一の FastAPI / PostgreSQL に保ちます（[ADR 0004](decisions/0004-receipt-gateway-and-ai-claims-assist.md)）。

理由は、**早すぎる物理分割は MVP を殺す** からです。サービス間通信・分散トランザクション・運用の複雑さを、外来カルテを作り切る前に背負うのは本末転倒。「Manta レセコンを単体販売する」「リリースサイクルが分かれる」「月次請求バッチや改定対応の負荷特性が分かれる」——そういう **必要が実際に来た時点で** `manta-rececon-api` として切り出す。それまではモノリスの速度を取ります。

#### なぜ import-linter でレイヤーを機械強制するのか

モジュラーモノリスの弱点は、「境界が口約束だと、いつの間にか溶ける」ことです。そこで Manta は、依存方向（`admin → gateway → rececon → inpatient → karte → master_data → auth → common` の一方向）を [import-linter](https://import-linter.readthedocs.io/) の契約として [`backend/pyproject.toml`](../backend/pyproject.toml) に明記し、**CI で逆流を検出** します。下位レイヤーが上位を import したら、ビルドが落ちる。

設計の意図を、レビュアーの善意ではなく **機械** に守らせる。これが「将来分割できる状態を、今のうちに保証する」唯一の現実解だと考えました。

#### なぜ FHIR を「データモデル」ではなく「ゲートウェイ」に置くのか

ここは意図的な判断です。FHIR をそのまま DB スキーマにすると、相互運用性は上がる一方で、**日々の臨床ロジックが FHIR リソースの抽象度に引きずられて重くなる**。

そこで Manta は、真実の源を **ドメイン固有の ORM**（`patients` / `conditions` / `observations` / `chart_notes` / 各種オーダ）に置き、[`gateway/fhir/`](../backend/app/modules/gateway/fhir/) のマッパーが **必要なときだけ** ORM ↔ FHIR R4B / JP Core を相互変換します。内側は素直なドメインモデル、外向きは標準規格。**「相互運用性」と「実装のしやすさ」を両取り** する設計です。

そしてこの「標準規格で外に開いている」状態こそ、**AI エージェントや外部サービスが自由に動くための前提** になります。FHIR を土台に据えるのは、相互運用のためだけでなく、来るべきエージェント時代への布石でもあります。エージェント側の入口は MCP（Model Context Protocol）で開く計画です——システム連携は FHIR、エージェント操作は MCP、どちらも gateway に閉じ込める、という役割分担にしています（[ADR 0007](decisions/0007-mcp-agent-interface.md)・[MCP 戦略](MCP_STRATEGY.md)）。

#### なぜ ORCA は「アダプタ」に閉じ込めるのか

日本のレセコンの事実上の標準である ORCA とは、[`gateway/orca/`](../backend/app/modules/gateway/orca/) のアダプタ経由で連携します。ORCA 固有の API 形式・エラーコードは、このアダプタの中だけに閉じ込め、カルテ／レセコン本体には漏らしません。これにより、**将来 ORCA 以外のレセコンや病院 HIS を後から足せる** ようにしています。

なお、ORCA の CLAIM 通信機能は 2026 年 3 月末で廃止予定のため、連携は CLAIM ではなく **日レセ API** 前提で設計しています（[ADR 0004](decisions/0004-receipt-gateway-and-ai-claims-assist.md)）。

#### なぜ認証を Argon2 + JWT で自前実装するのか

Phase 1 では、`利用者ID + パスワード` を Argon2 でハッシュ化し、ログイン成功時に JWT を発行、以降の API を `Authorization: Bearer` で保護する——という素直な自前実装にしています（[`backend/README.md`](../backend/README.md)）。役割（`医師` / `管理者`）は JWT に載せ、管理者専用 API は `require_role` で守ります。外部 IdP への接続は、必要になった段階で足す方針です。

### フロントエンド：React + Vite + Tailwind v4 + Radix（StyleSeed / Notion skin）

#### 大原則：レガシー EMR の「多色・高密度」を、捨てる

Manta の UI の North Star は **モダン SaaS（Notion / Linear / Vercel / Stripe）水準** です。レガシー EMR にありがちな、画面いっぱいの多色ボタン・高密度の表・点滅するアラート——これらを **採用しません**。医師がパワーユーザーとして高速に処理でき、かつ目が疲れない画面を作ります。

#### 紆余曲折：デジタル庁デザインシステムから離脱した

最初は、公的医療領域との親和性とアクセシビリティ（WCAG 2.2 AA）を狙って、**デジタル庁デザインシステム** を踏み台にしました。しかし、実際に取り込んでみて 5 つの非整合に直面しました（[ADR 0001](decisions/0001-design-system-digital-cho-and-pivot.md)）：

1. コンポーネント粒度が「Web 公文書」向けで、ダッシュボード / ワークフロー UI に組み直しが必要だった
2. カラートークンが業務システム調で、Notion ライクな温かい中立色（warm neutrals）を作りづらかった
3. タイポグラフィスケールが読み物向けで、クリニカル SaaS の情報密度に合わなかった
4. 彩度の高いセマンティックカラーが画面内で衝突し、「アラートを見せたい時にだけ目立つ」階層が組めなかった
5. 「密度の異なる情報をどう同居させるか」の設計言語がなかった

**公的デザインシステムは「公的 Web 表現の標準化」が目的であって、複雑な SaaS の情報設計ではない。** この学びを ADR に残し、踏み台を乗り換えました。アクセシビリティ要件（WCAG 2.2 AA）と「North Star = モダン SaaS」という上位原則は維持しています。

#### なぜ StyleSeed + Notion skin なのか

後継として [StyleSeed](https://github.com/bitjaru/styleseed)（69 の設計ルール + Radix ベースの UI プリミティブ + Claude Code スキル群）を採用し、スキンは **Notion skin 単独** に絞りました（[ADR 0002](decisions/0002-styleseed-adoption.md)）。

理由は、**カルテは本質的に「記録ドキュメント」** だからです。Notion の Warmth & Approachability 哲学（広い余白・温かい中立色・content-first）が、SOAP 記録を書く体験と最も整合します。Linear の Precision & Density はカルテ本文には密度が高すぎる——必要になれば、右ペインのオーダーキューだけ Linear 哲学に寄せるハイブリッドを別 ADR で検討します。

#### なぜ Tailwind v4 / Radix / class-variance-authority なのか

StyleSeed が Tailwind v4 前提であること、そして **Radix UI + cva + lucide-react という shadcn の標準体系に乗る** ことで、Web の知見とライブラリエコシステムにそのまま接続できるからです（[ADR 0002](decisions/0002-styleseed-adoption.md)）。独自最適化の自由度は多少捨てますが、それで十分という判断です。カラーは Apple HIG（apple.com/jp）準拠の体系を採用しています（[ADR 0003](decisions/0003-color-system-apple-hig.md)）。

### マスタデータ：保険診療の現実から逃げない

カルテだけなら、もっと早く作れます。Manta があえて重い道を選んでいるのは、**日本の保険診療の現実を、正面から飲み込む** と決めたからです。MEDIS-DC の ICD10 対応標準病名マスター、診療報酬点数表、医薬品（YJ / HOT コード）、PMDA 電子添文、レセプトコメント——これらを取り込み、施設別の運用ルールまで扱えるようにしています。

「マスタの取り込みと改定対応」は地味で、運用負荷も高い。でも、ここを避けたら現場で会計に流れず、価値が半分になる。**難しさを隠さず、説明可能な形で扱う** ——それが現場に届くプロダクトの条件だと考えています。

### ライセンスとブランド：Apache 2.0 一本 + Powered by Manta

#### なぜ Apache 2.0 に「統一」したのか

一度は、商用 SaaS 化を 2 年間防げる **FSL（Functional Source License）** や、領域ごとにライセンスを分ける 3 層分割も検討しました。しかし最終的に、**リポジトリ全体を Apache 2.0 一本に振り切りました**（[ADR 0005](decisions/0005-oss-process-economy-and-license.md)）。

理由は **普及の最大化** です。Kubernetes / Android / TensorFlow / Spark——世界を獲った OSS の定番が Apache 2.0 であり、特許条項がコントリビューターを守り、大企業にも採用されやすい。FSL や 3 層分割は商用保護を残せる反面、説明コストが高く、コントリビューターに「自分の貢献が将来クローズドにされるのでは」という不安を与え、共創スピードを落とします。**「保護を残す」より「本気で開く」ことを、競争優位に選びました。**

#### なぜ「Powered by Manta」なのか

Firefox/IceWeasel 的な「fork に名前を使わせない（防御）」ではなく、Intel Inside / Powered by Vercel / Built on Stripe に倣い、**「fork や派生に Manta 由来を明記してもらう」** 方を選びます。Apache 2.0 §4(d) の NOTICE 条項に attribution 要件を書けば、派生物もそれを引き継ぎます。`Powered by Manta` は商用サービスでも自由に使えます。

考え方はシンプルです——**名前を隠させるより、出典を明記してもらうほうが、良い形は広く伝わる。** Manta が使われるほど、Manta の名前も一緒に広がっていく。詳細は [ADR 0005](decisions/0005-oss-process-economy-and-license.md) に。

#### 商用 fork リスクは、受容する

既存レセコン大手や HIS ベンダーが Manta を fork して自社製品化する可能性はあります。それでも Apache 2.0 を選んだのは、**コミュニティ・ブランド・ドメイン知識・実装速度は fork できない** からです。そもそも私たちは「勝って市場を奪う」ことより「理想の形を広く使ってもらう」ことを優先しているので、複製されること自体は脅威ではありません。むしろ広がってくれるなら歓迎です。

---

## IV. 紆余曲折ごと、公開する

ここまで読んで気づいたかもしれません。Manta は **方針転換を隠していません**。

- デザイン基盤：デジタル庁 → StyleSeed / Notion skin（[ADR 0001](decisions/0001-design-system-digital-cho-and-pivot.md) → [0002](decisions/0002-styleseed-adoption.md)）
- ライセンス：FSL / 3 層分割の検討 → Apache 2.0 一本（[ADR 0005](decisions/0005-oss-process-economy-and-license.md)）

普通の製品開発なら、こうした「回り道」は表に出しません。でも Manta は逆です。**詰まった所、間違えた所、考え直した所——その全部が、同じ課題に挑む人への地図になる。** 完成した結論だけでなく、結論に至る過程に価値がある。それがプロセスエコノミーだと信じています。

---

## V. だから、一緒に作りたい

<!-- ▼ たたき台: 長島さんの声で自由に上書きしてください -->

Manta は、医師一人の理想では完成しません。

算定の現実を知っているのは医療事務です。スケールする設計を知っているのはエンジニアです。事業として続ける道を知っているのは投資家やパートナーです。そして、現場で本当に必要なものを知っているのは、明日も患者さんの前に座る医師と看護師です。

**この 4 つの視点が、同じリポジトリの上で出会えたら。** ブラックボックスだった医療ソフトを、みんなで開けて、作り直せたら。それは一企業のプロダクトを超えた、**日本の医療 IT の「共有財産」** になるはずです。

Issue を立てるのでも、コードを書くのでも、設計に異論を唱えるのでも、ただ Star を付けて見ていてくれるのでもいい。**あなたの視点が、Manta を一段ずつ良くします。**

ようこそ、Manta へ。一緒に作りましょう。
