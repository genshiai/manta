# ADR-0004: モジュラーモノリスを採用（マイクロサービス不採用）

## ステータス

承認済

## 背景

電子カルテシステムの設計パターンとして、マイクロサービスアーキテクチャとモジュラーモノリスを検討した。将来的には AI サービスを分離する計画がある。

## 決定

**モジュラーモノリスで始める。** マイクロサービスへの分離は、実際に必要になった時点で行う。

## 理由

### マイクロサービスを最初から採用しない理由

1. **チーム規模**: 少人数で始めるプロジェクトに分散システムの複雑性は不要
2. **開発速度**: サービス間通信、分散トランザクション、デプロイパイプラインが一気に増える
3. **開発環境**: `docker compose up` で開発環境が立ち上がることが最優先。サービスが5個あると起動だけで困難になる
4. **全体像の把握**: OSS コントリビューターが1つのリポジトリで全体像を把握できることが重要

### モジュラーモノリスの設計

```
1つの FastAPI アプリ内で、モジュール間の境界を import-linter で強制する。

┌─────────────────────────────────────┐
│           FastAPI App                │
│                                      │
│  ┌──────────┐  ┌──────────────┐     │
│  │ Charting  │  │ Prescription │     │
│  │ Module    │  │ Module       │     │
│  └──────────┘  └──────────────┘     │
│  ┌──────────┐  ┌──────────────┐     │
│  │ Patient   │  │ AI Service   │     │
│  │ Module    │  │ (interface)  │     │
│  └──────────┘  └──────────────┘     │
│                                      │
│         PostgreSQL                   │
└─────────────────────────────────────┘
```

### マイクロサービスへの移行パス

将来 AI モジュールを分離する場合:

```
┌──────────┐    ┌──────────────────┐
│ Main App │───→│ AI Microservice  │
│ (FastAPI)│←───│ (Python/LLM)     │
└──────────┘    └──────────────────┘
  gRPC or メッセージキュー（NATS / Redis Streams）
```

domain/ 内に Protocol（インターフェース）を定義してあるため、実装を外部サービスに差し替えるだけで分離できる。

## 帰結

- 1つのリポジトリ、1つのデプロイ単位
- モジュール間の依存は import-linter で CI に強制
- domain/ 内に AI サービスのインターフェース（Protocol）を定義
- 実装は infrastructure/ に置き、将来的に外部サービスに差し替え可能
- マイクロサービスへの移行は、パフォーマンスやスケーラビリティの問題が実際に発生してから判断する
