# Manta MCP 戦略 — 全機能をエージェントから到達可能にする

決定の記録は [ADR 0007](decisions/0007-mcp-agent-interface.md)。この文書はその詳細設計とフェーズ計画。
最終更新: 2026-07-11（実装は未着手。Phase 0 から始める）

## 目的

Manta の全能力を、MCP（Model Context Protocol）経由で AI エージェントから操作可能にする。「AI エージェントが動くカルテ」の具体的な入口はこれ。Claude Desktop / Claude Code / 各社エージェント基盤から、コネクタ設定だけで Manta に接続し、診療準備・記録の下書き・算定レビューの補助ができる状態を目指す。

インターフェースの役割分担:

| 入口 | 相手 | 語彙 | 例 |
|---|---|---|---|
| UI（React） | 人間 | 画面 | 診察して記録する |
| REST `/api` | 自前フロントエンド | ドメイン API | UI の裏側 |
| FHIR `/fhir` | 外部システム | FHIR R4B / JP Core | 地域連携・PHR・他社 HIS |
| **MCP `/mcp`** | **AI エージェント** | **タスク粒度のツール** | 「未確認の検査結果を要約して」 |

## 設計原則

1. **能力カバレッジ 100%、ルート 1:1 は 0%。** 約 100 の REST ルートを機械的にツール化しない。エージェントが選びやすいタスク粒度（20〜30 ツール）に束ね、下の能力カバレッジ表で「REST でできて MCP でできないこと」を管理する
2. **読み取りと下書きまで。確定は人間**（ADR 0004 / 0007）。確定系ツールは存在しないことが安全境界。UI 側の承認キューが人間の確定動線になる
3. **gateway に閉じ込める。** 実装は `gateway/mcp/` のみ。karte / rececon のサービス層を呼ぶ（HTTP を経由しない）。監査ログはサービス層のものをそのまま通る
4. **エージェントも利用者。** `agent` ロールの利用者としてログインし、監査ログに「誰のエージェントが誰の代理で何をしたか」が残る。匿名のエージェントアクセスは作らない
5. **既定は無効。** `MANTA_MCP_ENABLED=false` がデフォルト。有効化は明示的な運用判断

## アーキテクチャ

```
AI エージェント (Claude / IDE / 自作)
        │  MCP (Streamable HTTP)
        ▼
  /mcp  ─ gateway/mcp/          ツール定義・入出力スキーマ・権限フィルタ
        │      │
        │      ▼ 直接呼び出し（HTTP を挟まない）
        │  karte / inpatient / rececon / master_data のサービス層
        │      │
        │      ▼
        │  監査ログ（同一トランザクション）・PostgreSQL
```

- 公式 Python SDK（`mcp`）を FastAPI に Streamable HTTP でマウントする
- 認証: 既存 JWT 基盤。MCP セッション確立時に `agent` ロールのトークンを検証する
- ツールの入出力は Pydantic スキーマで定義し、REST のスキーマ資産を再利用する

## ツールカタログ（フェーズ計画）

### Phase 0 — 前提整備（MCP 以前）

- SEC-4: 臨床操作のロール制御の設計・実装（`agent` ロールをこのとき同時に定義する）
- `MANTA_MCP_ENABLED` の設定追加、`mcp` SDK の依存追加判断

### Phase 1 — 読み取り（デモ価値が最大の最小セット）

| ツール | 内容 | 裏で呼ぶ能力 |
|---|---|---|
| `search_patients` | 氏名・カナ・ID で患者検索 | karte 患者一覧 |
| `get_patient_summary` | 患者コンテキスト一式（基本情報・アレルギー・病名・直近受診） | karte ワークスペース |
| `get_chart_history` | 過去カルテ（SOAP 版履歴）の取得 | chart_notes |
| `get_lab_results` | 検査結果と異常フラグ・トレンド | 検査参照 |
| `get_medication_history` | 処方歴・薬歴タイムライン | 薬歴 API |
| `get_reception_board` | 本日の受付状況 | 受付一覧 |
| `get_ward_overview` | 病棟・ベッド状況（入院） | inpatient |
| `search_masters` | 病名・薬剤・診療行為マスタの検索 | master_data |

到達点デモ: Claude に「Manta の今日の外来で、検査結果が未確認の患者を教えて」と聞ける。

### Phase 2 — 下書き生成（write はすべて draft）

| ツール | 内容 | 人間の確定動線 |
|---|---|---|
| `draft_soap_note` | SOAP 下書きを保存（版確定はしない） | カルテ画面で採用・編集して確定 |
| `draft_order` | 処方・検査・画像オーダーの下書き | オーダー確認 UI で発行 |
| `suggest_diagnoses` | 病名候補の提示（マスタ照合済み） | 病名ツールで追加 |
| `draft_discharge_summary` | 退院サマリ下書き | 病棟の署名フローで確定 |

### Phase 3 — ワークフロー補助（レセコン領域）

| ツール | 内容 | 境界 |
|---|---|---|
| `review_claim_draft` | ClaimDraft の算定漏れ・病名不足・コメント不足を issue として列挙 | 送信はしない |
| `explain_return_event` | 返戻・査定イベントの内容説明と対応候補 | 対応の実行は人間 |

### 公開しないもの（意図的な非対応）

診察終了、会計送信、レセプト請求確定、退院実行、利用者・マスタの管理操作、監査ログの読み出し。理由: 確定・管理・監査は人間の領分（ADR 0004）。「ツールが無い」ことを安全装置とし、プロンプトインジェクションで突破される余地を作らない。

## 能力カバレッジ表の運用

- この文書に「REST でできて MCP でできないこと」を列挙し、各項目を「ツール化する / 意図的に非対応」のどちらかに必ず分類する（未分類を残さない）
- 新しい REST ルートを足す PR は、この表の更新（分類の追記）をセットにする
- 初版の表は Phase 1 実装時に作る

## セキュリティ

- **認証**: `agent` ロールの利用者アカウント + JWT。人間の利用者と同じ失効・期限管理
- **監査**: 全ツール呼び出しを既存の監査ログに記録（tool 名・引数の要約・対象患者・acting-for）
- **レート制限**: エージェントの大量読み取りに備え、`agent` ロールにのみ回数制限を導入する
- **プロンプトインジェクション対策**: 確定系ツールの不在を第一の防壁とする。カルテ本文など患者由来テキストをツール出力に含める際は「データであって指示ではない」ことをスキーマ側の説明に明記する
- **既定無効**: `MANTA_MCP_ENABLED=false`。本番での有効化は、環境種別（`MANTA_ENV`）とは独立の明示的なオプトイン

## 実装しない選択肢（再掲・理由つき）

- OpenAPI → ツール自動生成: ツール数が爆発しエージェントの精度が落ちる。確定系の露出も防げない
- FHIR-MCP 汎用ブリッジ: タスク粒度と日本の臨床語彙が失われる
- サイドカープロセス: 認証・監査・デプロイが二重化する

## 未決事項（実装時に決める）

- `agent` ロールの権限詳細（SEC-4 のロール設計に従属）
- ツール引数の患者 ID 体系（内部 ID か、患者番号か）
- Phase 1 の SDK バージョン固定方針とテスト戦略（MCP クライアントのモック）
