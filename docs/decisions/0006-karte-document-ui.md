# 0006. カルテUIをドキュメント型「読む・書く・作業する」に転換

- **Status**: Accepted
- **Date**: 2026-07-05
- **Deciders**: 長島大智（GENSHI AI）+ Claude Code での比較モック検討（2026-07-04〜05）
- **Tags**: design-system, frontend, karte, ux, ai

## Context（なぜこの決定が必要か）

OSS公開を前に、カルテ画面（`frontend/src/components/chart/`）の UX が未成熟だった。具体的な問題は実測で確認済み：上部タブ8個・右ペイン320pxに約47操作子（AIチャット常駐+4キュー+4タブ式追加Dialog）・機能ごとにボタンが増殖し「3クリック以内」原則（frontend/CLAUDE.md）と乖離。

統合思想の異なる4案（A 静かな2号紙=3ペイン / B ドキュメント型 / C エージェント同乗 / D キュー駆動）を同一診察シナリオのモックで比較し、ユーザーは **B（ドキュメント型）** を選択。追加の設計検討（既存カルテのWeb調査：エムスリーデジカル・BML Qualis・MI・RA・Is・Epic Storyboard/SmartPhrase・温度板の看護教材、および既存カルテ UI の私的比較分析）を経て以下が確定した。

## Decision（何を決めたか）

1. **カルテ＝1本のスクロール文書（シート）**。診察・検査・処方・画像・文書・入院までを1本の時系列ストリームで表示する。タブは廃止し、絞り込みは「レンズ」（すべて/診察/検査/処方/画像・文書）のみ。
2. **3状態モデル**：View（読む・既定）／ Write（本日ブロックのその場展開・書くことに集中）／ Work（⌘O コンポーザ＝従来オーダーポップアップの現代解釈：背景が透ける・キーボード完結・確定するとシートの行為列に着地・ページ更新なし）。
3. **日ブロックは2号紙の現代化**：内部を「記述（SOAP 14.5px）｜行為+点数（12px）」の左右2カラムにする（デジカル・Qualis と同じ、日本の医師の手癖に整合）。
4. **カラムは既定で非表示（1カラム）**。常時表示は患者バー（安全要件）と1行AIサマリー帯（34px）の2つだけ。左（患者基本+サマリー全文+カレンダー）と右（エージェント）は召喚式で、**ピン留め**により常駐化できる（overlay-first, pin optional）。既定ピンはロールの属性（病棟看護=温度板ピン等）。
5. **AIの置き場は4つに限定**：①常時=1行AIサマリー（展開でAIOカード） ②提案=エージェントトレイのカード（確定は医師のみ） ③召喚=／メニューのAI項目と⌘J ④随伴=録音→下書き→レビューのスクライブ。右ペインへのAIチャット常駐は廃止。
6. **AIサマリーは Google AI Overviews 型を初回展開の既定**とし、読了・折畳で1行ストリップに畳まれる（同一コンポーネントの2状態）。生成物には根拠リンク・更新時刻・生成範囲・免責を必ず付ける。
7. **「／」の文法を固定**：`／`=コマンド/ブロック挿入、`@`=データ差込、`⌘O`=コンポーザ。よく使うものは「この患者」×「自分」の2層履歴（使用回数つき・数字キー即実行）。Epic SmartPhrase の2層辞書に倣う。
8. **入院は温度板を継承**：標準配色（体温=青・脈拍=赤・血圧=∨∧、看護教材準拠）・暦日+病日の2段軸・上=重ね折れ線/下=観察・与薬グリッド。ヒーローサイズ（シート幅いっぱい・数値直書き・‹›期間送り+横スクロール）。入院はストリームの1ブロック。
9. **臨床画面はライト基調で固定**。ダークテーマはアプリの chrome / ドキュメントページ側にのみ適用し、カルテ・温度板等の臨床画面には適用しない（病院での受け入れ性を優先）。
10. 仕様の正本は [`docs/KARTE_UI_SPEC.md`](../KARTE_UI_SPEC.md)、ビジュアルの正本は [`docs/mock-html/karte-b.html`](../mock-html/karte-b.html)。`frontend/CHART-DESIGN.md`（3ペイン+8タブ前提）は本 ADR により旧方針となる。

## Consequences（帰結）

### Positive
- ボタン過多の構造的解消（機能は場所ではなく、／・⌘O・提案カード・レンズに属する）
- 既存カルテの手癖（2号紙・縦スクロール・Do/セット・温度板・患者バナー）を保ったままモダナイズできる
- 提案カードの中身は既存のルールDSL・PMDAチェック・処方複写APIの出力で成立するため、LLM完成前から「AIエージェントカルテ」の画面が嘘なく動く
- 外来と入院が同一の画面文法になり、学習コストが1回で済む

### Negative
- RecordPane/OrderPane の大規模改修が必要（8ビュー→シート、4タブDialog→コンポーザ）
- ／メニュー・コンポーザの検索基盤（薬剤/検査/セット/算定の横断）を整備するコスト
- ブロックエディタ的な編集体験（その場展開）はフォーカス管理・自動保存の実装難度が高い

### Neutral / Trade-offs
- 3ペインは「ピン留めした状態」として残る（機能削除ではなく既定の変更）
- 受付・レセプト画面の同文法再設計は別スコープ（本 ADR はカルテのみ）

## Alternatives Considered（他に検討した選択肢）

- **A 静かな2号紙（3ペイン完成形）**: 学習コスト最小だが「AIエージェントカルテ」の物語を画面が語れない。骨格はピン留め状態として吸収。
- **C エージェント同乗（3ペイン+提案トレイ）**: 提案トレイは採用するが、常駐カラムとしてではなく召喚+ピンで。
- **D キュー駆動（Linear風）**: カルテではなく受付画面の再設計として採用予定。
- **常設3カラム維持**: EMR界の通常（デジカル3ペイン・Epic Storyboard常駐）だが、シート自体が文脈を運ぶ本設計ではカラムの仕事が消えるため既定にしない。
