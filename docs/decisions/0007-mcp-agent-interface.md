# 0007. MCP を AI エージェント向けの第一級インターフェースとして gateway に追加する

- **Status**: Accepted（実装は未着手。フェーズ計画は [MCP_STRATEGY.md](../MCP_STRATEGY.md)）
- **Date**: 2026-07-11
- **Deciders**: 長島大智（GENSHI AI）
- **Tags**: gateway, ai-agent, mcp, architecture, security

## Context（なぜこの決定が必要か）

Manta の出発点は「AI エージェントが当たり前に動く電子カルテ」（[why-manta](../why-manta.md)）。しかし現状、エージェントが Manta を操作する経路が無い。REST API は約 100 ルートあるが人間の UI 専用で、外部 AI から見ると閉じている。FHIR ゲートウェイはあるが、これはシステム間のデータ交換の標準であって、「今日の外来で検査結果が未確認の患者は？」のようなタスク実行の入口ではない。

一方で MCP（Model Context Protocol）は、LLM エージェントにツールを公開する事実上の標準として定着した。Claude、主要 IDE、各社エージェント基盤が対応済み。Manta の全機能をエージェントから到達可能にするなら、独自プラグイン API を発明するのではなく MCP に乗るのが自然になった。

## Decision（何を決めたか）

1. **MCP を FHIR・ORCA と並ぶ gateway の第 3 のアダプタとして追加する**。実装は `backend/app/modules/gateway/mcp/`。FHIR = システム間のデータ標準、MCP = エージェントの操作標準、と役割を分ける。
2. **同一プロセスにマウントする**（FastAPI に Streamable HTTP で `/mcp` を生やす）。別プロセスのサイドカーにはしない。モジュラーモノリスの方針（ADR 0004）どおり、認証・監査ログ・トランザクションを REST と共有する。
3. **REST ルートの 1:1 自動ラップはしない**。約 100 の CRUD ルートをそのままツール化すると、エージェントのツール選択精度が落ち、確定系操作まで露出する。**「全能力への到達」を目標に、タスク粒度で束ねたツールカタログを手で設計する**（カタログと能力カバレッジ表は [MCP_STRATEGY.md](../MCP_STRATEGY.md)）。
4. **確定系操作はツールとして公開しない**。ADR 0004 の「AI は確定しない。人間が確定する」を MCP のツール面に適用する。読み取りと下書き（draft）生成までがエージェントの領分。診察終了、会計送信、レセプト請求、退院実行のツールは作らない。
5. **エージェントは専用ロールの利用者として認証する**。人間と同じ JWT 基盤に `agent` ロールを追加し、全ツール呼び出しを監査ログに記録する（誰のエージェントが、誰の代理で、何をしたか）。ロール体系の詳細設計は SEC-4（臨床操作のロール制御）と同時に行う。
6. **既定は無効**。`MANTA_MCP_ENABLED`（デフォルト `false`）で明示的に有効化する。

## Consequences（帰結）

### Positive

- 「AI エージェントが動くカルテ」が看板ではなく実装になる。Claude Desktop / Claude Code などの既存エージェントが、コネクタ設定だけで Manta に接続できる
- ツールカタログの設計がそのまま「エージェントに何をさせ、何をさせないか」の仕様書になり、医療 AI の安全境界を説明可能にする
- gateway に閉じ込めるため、karte / rececon 本体は MCP の存在を知らずに済む（ADR 0004 の境界哲学と一貫）

### Negative

- ツールカタログの手設計と維持コストを抱える（ルート追加のたびにカバレッジ表の更新判断が要る）
- MCP 仕様はまだ変化が速く、SDK 追従のコストがある
- エージェント経由の大量読み取りという新しい攻撃面が生まれる（レート制限と監査で受ける）

### Neutral / Trade-offs

- 確定系を公開しない設計は、エージェントの自律性を意図的に制限する。「AI が全部やる」デモ映えより、医療での説明責任を優先した
- SEC-4 のロール設計が MCP の前提になるため、着手順が固定される（ロール設計 → MCP Phase 1）

## Alternatives Considered（他に検討した選択肢）

- **OpenAPI からツールを自動生成**: 実装は最速だが、100 個の CRUD ツールはエージェントの精度を落とし、確定系の露出を防ぐ仕組みを別に作る羽目になる。不採用
- **FHIR ゲートウェイを汎用 FHIR-MCP ブリッジで公開**: 相互運用の語彙（Resource/Bundle）はタスク実行には粒度が粗く、日本の臨床語彙（病名・処方・算定）が失われる。システム連携は FHIR、エージェントは MCP と分けるほうが良い。不採用
- **独自のプラグイン/Function API**: エコシステムが無い。MCP が既に標準。不採用
- **サイドカー MCP サーバー（REST を叩く別プロセス）**: 認証の二重管理と監査の分断が起きる。デプロイも 2 つになる。モノリス内マウントで足りる。不採用
